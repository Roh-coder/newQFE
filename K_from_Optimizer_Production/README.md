## 1. Quick-Start / Overnight Test

```bash
# ── on the offline PC ─────────────────────────────────────────────────────
# 1. Copy the source directory (or clone the repo)
cp -r K_from_Optimizer_Speedup_Upgrade  ~/optimizer_production
cd ~/optimizer_production

# 2. Build the C++ simulator (one-time, ~10 s)
make

# 3. Install Python dependencies (one-time, in your venv)
python -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt

# 4. Run the overnight validation suite
bash K_from_Optimizer_Production/run_overnight.sh ~/optimizer_production

# 5. In the morning, check results
python K_from_Optimizer_Production/check_overnight.py  ~/optimizer_production/results/_overnight/
```

`run_overnight.sh` launches four sequential 600-second runs (see
[section 2](#2-overnight-test-plan)) and writes a human-readable
`OVERNIGHT_REPORT.md` when finished.

## 2. Overnight Test Plan

The overnight suite validates three things in order:

| Run | Method | n_workers | reweight | Purpose |
|-----|--------|-----------|----------|---------|
| A | legacy CMA-ES | 1 | False | baseline β_c accuracy + timing |
| B | S4 (single-donor) | 1 | True | regression: current reweight=True |
| C | S4 multi-donor + fallback | 1 | True | **new code path** — accuracy probe |
| D | S4 multi-donor + fallback | 4 | True | **full upgrade** — speed + accuracy |

Each run uses `max_evals=40`, `cma_popsize=6`, `test_Lx=Ly=12`,
`n_traj_prod=10_000`, `no_vis=True` (no PNG overhead), `save_every=1`.
Four runs × 40 evals × ~8 s/eval (S4+4 cores) ≈ total wall ~70 min at
best, ~240 min at worst — comfortably within an overnight window.

## 3. Implementation Plan — S4 Multi-Donor Reweighting + 3-Pass Fallback

> **Status (2026-04-25):** Design complete, not yet coded.
> The single-donor path (`reweight=True`) is in production quality but
> fails on far-from-equilateral starts (mean |Δβ_c|=0.034, max=0.093).

### 3.1 Overview

Current code path when `reweight=True`:

```
eval (r1*, r2*)
  └─ find_beta_c_reweight()
       ├─ spawn parent MC at bracket midpoint  (reweight_n_traj traj)
       ├─ reweight χ(β) on dense grid
       ├─ GC fit → β_c estimate
       └─ if peak outside validity window: recenter up to 3×, then WARN
```

Target code path after upgrade (two-stage):

```
eval (r1*, r2*)
  └─ find_beta_c_s4plus()
       ├─ Stage 1: multi-donor lookup
       │    ├─ estimate β_c_est from S2 cache OR linear extrap from 2 nearest evals
       │    ├─ scan TraceStore: collect donors with |β_c_donor − β_c_est| ≤ δβ_valid
       │    ├─ CombinedReweighter(donors) → β_c, σ   [if N_eff gate passes]
       │    └─ if accepted: return  (status="reweight_multi", zero MC cost)
       │
       └─ Stage 2: 3-pass fallback
            └─ find_beta_c_legacy()  →  β_c, σ   (status="fallback_3pass")
```

### 3.2 New class: `TraceStore` in `mc_engine.py`

```python
class TraceStore:
    """In-memory store of (energy, M²) traces keyed by eval."""

    def __init__(self, cfg, lock=None):
        # _store: dict of {eval_id: TraceEntry}
        # TraceEntry: dataclass(r1, r2, beta_c, sigma_E, n_traj, E, M2)
        self._store: dict = {}
        self._lock  = lock or threading.Lock()
        self._pkl   = cfg.get("trace_store_pkl", None)  # path or None

    def add(self, eval_id, r1, r2, beta_c, sigma_E, E, M2):
        entry = TraceEntry(r1=r1, r2=r2, beta_c=beta_c,
                           sigma_E=sigma_E, n_traj=len(E), E=E, M2=M2)
        with self._lock:
            self._store[eval_id] = entry
            if self._pkl:
                self._safe_pickle_append(entry)

    def query(self, beta_c_est, donor_radius) -> list[TraceEntry]:
        """Return entries where |β_c_entry - β_c_est| ≤ donor_radius × σ_E/√N."""
        with self._lock:
            out = []
            for entry in self._store.values():
                delta_valid = donor_radius * entry.sigma_E / math.sqrt(entry.n_traj)
                if abs(entry.beta_c - beta_c_est) <= delta_valid:
                    out.append(entry)
            return out
```

**CONFIG keys to add to `run.py`:**

```python

"reweight_fallback":      True,   # fall back to 3-pass GC scan if all donors fail
"trace_store_pkl":        None,   # path to persist TraceStore for warm restarts
```

### 3.3 Updated `find_beta_c_reweight()` in `mc_engine.py`

Replace the existing recenter loop (lines ~200–250 of `mc_engine.py`)
with this logic:

```python
def find_beta_c_s4plus(cfg, geom, kappa, bracket,
                        trace_store, beta_c_est, dashboard=None):
    """Two-stage β_c finder: multi-donor reweight → 3-pass fallback."""

    # ── Stage 1: multi-donor attempt ─────────────────────────────────
    donors = trace_store.query(beta_c_est, cfg["reweight_donor_radius"])
    if donors:
        cr = CombinedReweighter(donors, geom["V"])
        beta_c, sigma, neff_min = cr.find_beta_c(bracket,
                                                   n_grid=cfg["reweight_n_grid"],
                                                   n_eff_floor=cfg["reweight_n_eff_floor"])
        if beta_c is not None:   # validity gate passed
            return beta_c, sigma, "reweight_multi", neff_min

        # single-donor fallback within Stage 1
        best = max(donors, key=lambda d: d.n_traj)
        sr = SingleReweighter(best, geom["V"])
        beta_c, sigma, neff_min = sr.find_beta_c(bracket,
                                                   n_grid=cfg["reweight_n_grid"],
                                                   n_eff_floor=cfg["reweight_n_eff_floor"])
        if beta_c is not None:
            return beta_c, sigma, "reweight_single", neff_min

    # ── Stage 2: 3-pass GC scan fallback ─────────────────────────────
    if cfg.get("reweight_fallback", True):
        beta_c, sigma = find_beta_c_legacy(cfg, geom, kappa, bracket, dashboard)
        return beta_c, sigma, "fallback_3pass", float("nan")

    # reweight_fallback=False: raise so the caller can handle it
    raise RuntimeError("All donors failed validity gate and fallback disabled.")
```

### 3.5 β_c estimator for donor lookup

Linear extrapolation from the two most recent evaluations:

```python
def _estimate_beta_c(self, r1, r2) -> float:
    """Rough β_c estimate at (r1, r2) for donor selection."""
    history = self.history   # list of EvalResult, chronological

    # S2 cache takes priority if available
    if self.betac_cache is not None:
        hit = self.betac_cache.lookup(r1, r2)
        if hit is not None:
            return hit[0]

    # Fall back to nearest-neighbour from history
    if len(history) == 0:
        return sum(self.cfg["beta_seed"]) / 2   # bracket midpoint

    dists = [math.hypot(h.r1 - r1, h.r2 - r2) for h in history]
    i_nn  = min(range(len(dists)), key=dists.__getitem__)
    return history[i_nn].beta_c
```

## 4. Implementation Plan — S3 Parallel Population Evaluation

> **Status (2026-04-25):** Infrastructure exists in `parallel.py`.
> `n_workers=1` preserves serial behaviour.  Set `n_workers > 1` to enable.
> Expected to be stable — use `n_workers=4` for overnight test Run D.

### 4.1 How it works

`parallel.py` wraps a `ProcessPoolExecutor`.  The CMA-ES generation
loop in `optimizer.py` already calls `parallel.map_generation(xs, eval_one)`.
With `n_workers=4` and `λ=6`:

```
generation wall time ≈ max(eval_time of slowest of 6 evals / 4 concurrent)
                      ≈ ceil(6 / 4) × per_eval   [ignoring Amdahl]
                      = 2 × 6–8 s  ≈ 12–16 s/generation  (vs 144 s legacy)
```

### 4.2 CONFIG keys

```python
"n_workers":       4,    # 0 = auto (min(popsize, cpu_count))
                          # 1 = serial (legacy behaviour, no overhead)
"worker_pinning":  False, # pin each worker to a core (Linux: taskset)
```

Set `n_workers = min(cma_popsize, os.cpu_count())` for best results.
`n_workers > cma_popsize` wastes cores (CMA-ES can only run λ
concurrent evals per generation).

### 4.3 RNG seeding (important)

Each worker **must** derive an independent seed.  The `parallel.py`
worker startup already uses `np.random.SeedSequence(master_seed).spawn(n_workers)`.
Verify by checking that the generation-level cost spread is consistent
with `~√popsize × σ_cost` — if all workers share a seed, the spread
collapses to ≈ 0 and the CMA convergence criterion fires prematurely.

### 4.4 Scratch directory layout

Each eval writes to `results/<run>/mc_scratch/eval{:04d}_r{r1:.4f}_{r2:.4f}/`.
With parallel workers these directories are created simultaneously;
they do not collide because the `eval_id` is globally unique (assigned
by the main process before dispatching workers).

### 4.5 Dashboard and visualizer in parallel mode

The dashboard connects via a `multiprocessing.Queue` that each worker
pushes `DashEvent` objects into.  The main process drains the queue
once per generation in `optimizer.run_cmaes()`.  Events arrive
out-of-order in wall-clock time; the dashboard and visualizer render
strictly by `eval_id` to keep frames monotone.

In parallel mode the β_c scan progress bar (Speedup 1 RPC not yet
landed) is suppressed per-worker — only the generation-level summary
is shown in the dashboard.

## 6. Performance Expectations

All timings on 12×12 test lattice, `n_traj_prod=10_000`, single core
unless stated.  Scale production MC time as `O(Lx·Ly·n_traj_prod)`.

### Per-evaluation breakdown

| Phase | Legacy (3-pass scan) | S4 fast path (multi-donor) | S4 fallback (3-pass) |
|-------|--------------------|--------------------------|--------------------|
| β_c scan | ~17 s | **~0 s** (reuse donors) | ~17 s |
| Production MC | ~6 s | ~6 s | ~6 s |
| **Total per eval** | **~23 s** | **~6–8 s** | **~23 s** |

### Per-generation wall time (λ=6)

| Method | 1 core | 4 cores | 8 cores |
|--------|--------|---------|---------|
| Legacy CMA-ES | 138 s | — | — |
| S4 multi-donor (gen 1, all fallback) | 138 s | 46 s | 23 s |
| S4 multi-donor (gen ≥ 2, 80% fast) | ~61 s | **17 s** | 9 s |
| S4 multi-donor (steady, ~95% fast) | ~46 s | **13 s** | 7 s |

### End-to-end speedup vs legacy CMA-ES, 1 core

| Configuration | Speedup |
|---------------|---------|
| S4 only, 1 core | ~2.3× |
| S3 only, 4 cores (no S4) | ~4× |
| S4 + S3, 4 cores | **~8–10×** |
| S4 + S3, ceiling (trace store full) | up to **~15×** |

> **Note:** The 8–10× figure assumes ~80% fast-path at steady state.
> With the multi-donor trace store covering the whole optimizer
> trajectory by generation 3, fast-path fraction rises to ~95%,
> approaching the ceiling.  Generation 1 is always full-fallback (no
> donors yet) — this is unavoidable and acceptable.

### At L=24, `n_traj_prod=50_000` (production scale)

Legacy per-eval: ~80 s.  S4 fast path: ~20 s.  S4+S3 (4 cores):
~10 s/eval wall → a 60-eval CMA-ES run completes in **~15 min** vs
**~80 min** legacy.
